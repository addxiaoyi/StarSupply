# 冬季远征与持续围城

StarSupply 读取 StarCore 的 `SeasonService`、`WarService` 与可选 `SiegeService`，对已绑定前线站的参战军队计算临时需求。采样在 Paper 服务线程每 5 秒执行，再把不可变数据交给补给工作线程。采样超过 15 秒或服务不可用时恢复普通需求，避免过期状态持续压制军队。

前线站还必须仍处于本国控制，并且军队与前线站位于同一世界、三维距离不超过 `army-frontline-radius`。默认服务半径 256 格，可配置为 32–2048 格。`SupplyStatus.frontAccess()` 区分 `CONNECTED`、`CONTROL_LOST` 与 `ARMY_OUT_OF_RANGE`。失守或军队超出范围时覆盖率为 0，不继续扣除该站物资；战时使用有界的缺补给战力，和平倍率仍为 1。重新控制领土或军队返回范围后恢复供应，同一周期已经消费的需求和物资记录不会重复扣除。

军队推进后，军需官可在新的本国已占领位置执行 `/supply front <新前线ID> <军队UUID或前缀>`。这会在同一个 SQL 事务中解除旧站的军队绑定并登记新站，旧站的库存、道路和运输合同留在原处，不能通过重新绑定传送货物。新站仍需要道路和真实运输补给。

| 条件 | 默认效果 |
| --- | --- |
| 前线世界处于 StarCore 冬季，且国家处于可战斗战争 | 粮食需求增加 25%，医疗增加 10%。 |
| 敌对参战国家的活跃器械正在围攻前线 128 格内的本国城墙 | 粮食、建材、工程需求随持续时间增加，30 分钟达到额外 50%。 |
| 围城解除、停战、观察过期或时钟回退 | 停止累积围城压力；下个未消费周期恢复对应普通需求。 |

围城判定同时要求器械为 `BESIEGING`、存活且可开火，目标城墙仍有生命、正在被同一器械围攻，目标所属国和世界匹配。仅器械靠近前线、和平时部署或攻击其他城墙不会产生压力。StarSupply 不创建战争、器械或城墙，也不替代 StarCore 攻城规则。

需求按原有国策效率计算基础值，再加季节与围城比例并向上取整，每类最多 100000 单位。配置额外比例各不超过 50%；同时冬季与围城也不超过基础粮食的两倍。小军队的一单位需求可能因取整变为两单位，GUI 显示实际整数需求。

同一军队、周期、资源首次消费后，SQLite 保存的 `consumption.demand` 成为该周期固定值。中途季节、国策、兵力或围城变化不会重复消费或改写这个周期。未消费的下一周期重新取样。充足补给、缺粮减益与国策战备系数继续使用有界战力倍率，不直接写入永久士气，也不会离线补扣历史消耗。

首次消费事务提交后，插件异步发布 `SupplyConsumptionEvent`，包含军队、国家、前线站、周期、需求和实际消耗量。事件 ID 由军队 UUID 与周期确定；监听器可据此去重。事件是提交后的通知，进程若在提交后、通知前退出，不保证重启时重发，不能把收到事件作为真实库存提交的唯一证据。

主数据库 v7 的 `campaign_siege` 保存前线连续围城开始与最近观察时间。短暂重启可以在连续性窗口内续接；默认超过 60 秒未确认、解除围城、停战或时间回退即清除连续压力。重启没有先采到有效 StarCore 状态时，不会凭旧记录制造围城。

配置位于 `campaign`：

```yaml
campaign:
  winter-food-extra: 0.25
  winter-medical-extra: 0.10
  siege-maximum-extra: 0.50
  siege-ramp-seconds: 1800
  siege-continuity-gap-seconds: 60
  siege-radius: 128
```

比例可设为 0 以关闭相应额外需求；围城半径 16–512 格，爬升时间 60 秒至 24 小时，连续性窗口 15 秒至 5 分钟。修改后重启。`/supply status`、军队 GUI 与 `SupplyStatus.campaign()` 展示当前冬季、围城秒数、围城额外比例和采样时间；每周期需求可能仍是本周期已锁定的旧快照。

自动化验证覆盖额外需求限幅、取整、连续性持久化、解除恢复及周期防重复消耗。完整 StarCore 实时联动以 [Paper 验收记录](PAPER-ACCEPTANCE.md) 为准。
