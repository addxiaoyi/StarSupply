# 库存、运输与付款恢复

库存操作锁绑定实际内部流程，而不是调用方持有的返回 future。取消、设置超时或手工完成公开结果不会撤销已受理的物理操作；真实流程结束（成功或失败）后才清理锁，防止重叠扣物或永久卡住。此行为有修复前两项失败、修复后五项通过的回归证据，并在当前构建的 Folia 实体退役、区块卸载/区域重建及持久回执恢复验收后核对停服存档。见 [构建记录](verification/workspace-inventory-cancellation-20261125.json) 与 [运行记录](verification/folia-region-retirement-20261125.json)。

StarSupply 只把授权国家、军队、领土、战况和资金操作交给 StarCore。主 SQLite `supply.db` 保存合同、实物批次和交接、消耗及待结算记录；`insurance.db` 保存保险的独立经济阶段，`tavern.db` 保存集合点与观察。一个服务器实例拥有这组 SQLite 和同一份玩家存档目录。备份或还原时应成组处理三个 StarSupply 数据库、StarCore 和世界玩家数据。

插件关闭时先停止接收操作，并使尚未开始的实体回调以失败结束，释放对应的库存操作占用。实体调度器在插件停用时取消任务，不保证执行玩家退役回调，因此不能只依赖该回调结束异步流程。已经开始的玩家存档操作保留自身完成权；尚未确认的 SQL 和库存收据继续按原有重连恢复规则处理。旧代次或已取消回调不能再次访问玩家。排队取消、执行中关闭、退役、跨代次和关闭竞态由 `EntityCallbacksTest` 验证；真实区域卸载和调度器退役的完整现场验收仍需单独证据。

重新启用还必须等待旧 SQL 线程完全停止、执行中的实体回调返回，以及完整库存异步流程释放占用。结果对象已完成或被取消，不等于实体回调及其同步完成链已经退出。SQL 提交固定本次生命周期和线程池，避免提交途中改投新线程池。实体和 SQL 任务遇到 `Error` 时也先结束结果、释放依赖占用，再把致命错误交给宿主；线程池随后继续处理已接收队列。同步启动库存流程抛出 `Error` 同样释放占用。关闭步骤逐项隔离普通异常与链接错误，并在 `finally` 中停止和排空 SQL 线程。新增回归包含取消执行中结果、完成链内重启屏障、致命异常传播及失败线程退出后的队列收尾；112 项完整构建测试和适用边界见 [生命周期加固记录](verification/workspace-lifecycle-hardening-20261125.json)。

保险恢复在同一进程内也检查遗留的 `STARTED`：无独立回执的保费扣款、国库入账和返还先转入 `REVIEW`，不能因结果写回回滚就再次调用。准备金、理赔和释放继续按原持久编号恢复。真实 SQLite 故障注入覆盖结果写入失败与复核写入失败，完整 119 项构建通过；外部经济调用使用测试替身，详见 [保险中断恢复](verification/workspace-insurance-interruption-20261125.json) 和 [保险规则](INSURANCE.md)。

| 步骤 | 成功条件 | 失败后的归属 |
| --- | --- | --- |
| 接收卖家实物 | SQLite 先预留采购单，持久化物品批次和唯一收据。玩家所在实体线程重新核对背包，再从同一次玩家保存验证收据。 | 确认没有改动时开放订单。无法确认玩家保存结果时冻结该批物资，重登恢复或管理员核对。 |
| 支付采购款 | StarCore 国库按毛额扣款、卖家按净额入账，SQLite 再把实物批次入库。配置了非零 TARIFF 的跨境合同会另由 StarCore `TaxationService` 将税款记入进口国国库。StarCore 报告 `INSUFFICIENT_FUNDS` 但 `balanceAfter` 仍足以覆盖付款时，保留同一结算并返回 `RETRY`，后续沿用原幂等凭证检查国库回执。 | StarCore 国库确认余额不足时可取回原物。关税或卖家入账结果不明时批次保持冻结。先独立核对卖家入账并用 `/supply reconcile <结算UUID> <paid|unpaid>` 确认卖家款；若卖家已收款但关税仍待核验，再用 `/supply reconcile-tax <结算UUID> <funded|unfunded>` 处理税款阶段。 |
| 发布运输合同 | 在同一个 SQLite 事务中锁定采购批次和开放合同，并生成唯一 convoy 风险值。 | 未结算的取消或超时解除锁定，实物仍在起点。同一物资批次后续重运沿用风险值，不能通过取消重抽。 |
| 支付运费 | 先登记唯一结算，再通过 StarCore 支付。确认后同一批次从起点移到目的地。 | 已确认的付款拒绝解锁起点物资。待核验期间不能再次交付或取消。 |
| 护送与路线风险 | 起运前最多 4 名本国玩家在起点加入护送队。护送人数、起运/绕行后的风险快照和准备时间保存在 SQL。护送者改为承运者时，在领取事务中移除其自己的护送登记。 | 自身不参与风险、计时或具体承运者保险报价的护送优惠；其他护送者最多降低 40% 路线风险并缩短 20% 运送时间。交付遭袭则运输为 `FAILED`、实物退回起点，不生成运费结算；重运仍用相同批次风险值。护送者无独立奖金。 |
| 退回原物 | 检查背包空间，持久化唯一退还收据，按原物品数据验证保存，再销掉 SQL 批次。 | 背包不足时整批保留。保存结果不确定时冻结再次领取。 |
| 军队消耗 | 以军队、周期 slot、周期长度和资源为唯一键。库存扣减与消耗记录同事务提交。只有仍受本国控制、与军队同世界且在服务半径内的前线消费。 | 同一周期重试不会再次消费。迁移后的旧记录周期长度未知，在匹配 slot 时仍阻止重复扣除。失守或超出范围时覆盖率为 0、保留物资；恢复后沿用本周期已有记录。停服期间不会补扣历史周期。 |
| 推进前线 | `/supply front <新ID> <军队>` 在同一事务中解除旧站军队绑定并创建新站。 | 旧站库存、道路和运输合同留在原处，新站需要真实物资补给；失败则整个绑定变更回滚。 |
| 战役额外需求 | 服务线程采样 StarCore 冬季与围城状态，工作线程记录连续性，再使用同一库存消费事务。 | 已消费周期的需求快照不变；停战、围城解除、过期观察或时间回退停止压力。 |
| 承运收入保险 | 独立保单先通过 StarCore 真实预留赔款，再收保费并记入国库，全部确认才激活。 | 不确定经济阶段冻结保单及运输；只对持久化 `RISK` 原因的实际遭袭触发理赔，超时、取消或普通运费拒绝不赔。 |

StarCore 的 `NationSpendingService` 提供幂等的国库扣款和退款凭证。玩家内部经济的发款接口没有可直接重放的持久凭证，因此适配器先写入发款开始记录。重新启动后，如果只能确认调用已经开始，就将该笔转人工核对。管理员应核对 StarCore 操作凭证、玩家账目和时间，再使用 `/supply reconcile <结算UUID> <paid|unpaid>`。确认未到账时会按照同一个扣款凭证退款。

StarCore 的 `INSUFFICIENT_FUNDS` 结果不总能单独证明余额不足。付款适配器同时收到足额 `balanceAfter` 时把本次结果视为可重试的国库写入冲突，不取消采购、不退款，也不生成新结算。真实余额不足仍按拒绝路径处理。v11 Paper 玩家回归观察到两笔 5.00 采购各结算一次并拒绝重复售货，但没有现场触发重试；回归分支由 `CorePaymentTest` 覆盖，运行证据见 [Paper v11 付款回归记录](verification/paper-v11-payment-retry-20261122.json)。

库存收据和背包同时写入 Paper 玩家存档。插件读回并同步该存档，然后提交本地 SQL。新版本以递归排序后的 Bukkit 物品序列化映射计算背包指纹，避免映射键遍历顺序变化造成误判；恢复旧记录时也会比对原 `serializeAsBytes` 指纹。收据缺失时不会仅凭背包数量推断已经扣除或退回。管理员可结合存档与日志使用 `/supply reconcile-inventory <收据UUID> <applied|untouched>`。没有足够证据时让记录继续保留待核对状态。

2026-11-22 的隔离 Paper v11 复测观察到组件映射顺序变化的旧待处理记录继续停留在 `REVIEW`，再凭玩家存档执行 `untouched` 核对后采购开放、交接标记为 `RETURNED`，且该交接没有结算。纯原版铁锭对照则自动清理旧交接并保留开放采购。另有一次验收监视器误关联到同采购单的旧 `RETURNED` 行，隔离副本产生一笔独立 5.00 的正常付款；该行已在验收证据中单独披露，不计入无结算恢复路径。详见 [Paper v11 库存指纹恢复记录](verification/paper-v11-legacy-fingerprint-recovery-20261122.json)。这次只验证 Paper，该构建尚未在 Folia 环境中复测。

当前主 SQL schema 为 v11。v3 增加跨国额度，v4 增加路线风险和护送成员，v5 增加批次遭袭值，v6 增加关税快照与阶段，v7 增加持续围城观察，v8 增加运输失败原因与不可变发生时间，v9 增加实物 FOOD 到 StarCore 原生补给的持久请求，v10 将周期长度加入该请求的唯一键以支持配置变化和历史消耗清理后的稳定去重。v11 将周期长度加入军队消费唯一键，并将已迁移的旧消费记录保留为周期长度未知的幂等保护记录，按统一时间戳保留七天。`tavern.db` 使用独立 v1 schema；`insurance.db` 当前为 v2，增加真实激活时间，v1 的旧活跃保单以已有持久创建/更新时间保守迁移。未起运等待期从激活时间计算，经济阶段等待核验不会提前耗尽起运窗口。主生命周期迁移测试覆盖旧结构迁移和原生补给待核验恢复；v10 原生补给回执及正常重启重放已在隔离 Folia 运行中验证。v11 已在独立 Folia 副本从 v10 数据库迁移，保留 10,470 条旧消费保护记录，并通过正常停服、重启和 SQLite 完整性检查；此运行没有玩家交易。Paper v10→v11 迁移也保留 10,470 条历史消费保护记录，并在两次启动后保留 78 条 30 秒周期的消费记录；该轮没有玩家交易，未验证原生补给回执重放。详见 [Folia v11 迁移记录](verification/folia-v11-schema-migration-20261122.json)、[Paper v11 迁移记录](verification/paper-v11-optional-plugin-migration-20261122.json) 及 [原生补给回执记录](verification/starcore-native-supply-receipts-20261121.json)。Paper 既有 v5→v6 及六类物资运行记录仍按各自构建哈希解释。

`SupplyConsumptionEvent` 在首次消费提交后异步通知，包含本次需求和实际消耗；唯一 ID 由军队 UUID、周期 slot 和周期长度确定。消费记录负责幂等，事件本身不保证在提交后崩溃时可靠重发。监听器异常不会回滚已经提交的真实消费，不能依靠事件是否收到决定再次扣库存。

含非零税额的订单把阶段保存在 `settlement_tax`：`QUOTED` 表示快照已保存，`FUNDING` 表示正在调用 StarCore，确认后为 `FUNDED`；异常或返回不确定时转 `REVIEW`。StarCore 当前 `TaxationService.fundTax` 对重复税务 ID 返回 0，且没有按交易 ID 查询税收回执的公开接口。卖家已收款而税额结果不明时，不能再支付卖家或仅凭余额推断税款状态；订单与实物批次保持冻结。管理员须从独立 StarCore 账务证据确认 `funded`，或确认未缴后通过保存的同一报价补缴，再执行对应的 `reconcile-tax` 选项。

运输遭袭在解除实物预留的同一个 SQL 事务中保存 `failure_reason=RISK` 与 `failed_at`，超时保存 `EXPIRED`。保险根据这个原始发生时间判断理赔，不以重启后的当前时间猜测，也不把所有 `FAILED` 当成遭袭。保险与主货物数据库分别提交时，维护轮询会重新连接保单和最终运输状态；确认过的款项不会因这次连接重放。保单经济阶段及 `/supply reconcile-insurance` 的证据要求见 [保险恢复](INSURANCE.md)。

主动取消运输或退保先检查货物仍处于 `OPEN/IN_TRANSIT`，再处理准备金。货物已经进入普通结算、遭袭失败、交付或关闭后，不能借退保取消既有理赔；维护过程按持久化运输结果完成保险。

路线风险扫描逐区块覆盖仓库间直线路径，包含穿越区块角点的保守邻格。超过 4096 个路径区块的道路不可规划：新建请求直接拒绝，旧记录视为封锁。这个上限防止不完整扫描把敌对占领区误判为安全路段。
