# 库存、运输与付款恢复

StarSupply 只把授权国家、军队、领土、战况和资金操作交给 StarCore。主 SQLite `supply.db` 保存合同、实物批次和交接、消耗及待结算记录；`insurance.db` 保存保险的独立经济阶段，`tavern.db` 保存集合点与观察。一个服务器实例拥有这组 SQLite 和同一份玩家存档目录。备份或还原时应成组处理三个 StarSupply 数据库、StarCore 和世界玩家数据。

| 步骤 | 成功条件 | 失败后的归属 |
| --- | --- | --- |
| 接收卖家实物 | SQLite 先预留采购单，持久化物品批次和唯一收据。玩家所在实体线程重新核对背包，再从同一次玩家保存验证收据。 | 确认没有改动时开放订单。无法确认玩家保存结果时冻结该批物资，重登恢复或管理员核对。 |
| 支付采购款 | StarCore 国库按毛额扣款、卖家按净额入账，SQLite 再把实物批次入库。配置了非零 TARIFF 的跨境合同会另由 StarCore `TaxationService` 将税款记入进口国国库。 | StarCore 国库扣款遭拒后可取回原物。关税或卖家入账结果不明时批次保持冻结。先独立核对卖家入账并用 `/supply reconcile <结算UUID> <paid|unpaid>` 确认卖家款；若卖家已收款但关税仍待核验，再用 `/supply reconcile-tax <结算UUID> <funded|unfunded>` 处理税款阶段。 |
| 发布运输合同 | 在同一个 SQLite 事务中锁定采购批次和开放合同，并生成唯一 convoy 风险值。 | 未结算的取消或超时解除锁定，实物仍在起点。同一物资批次后续重运沿用风险值，不能通过取消重抽。 |
| 支付运费 | 先登记唯一结算，再通过 StarCore 支付。确认后同一批次从起点移到目的地。 | 已确认的付款拒绝解锁起点物资。待核验期间不能再次交付或取消。 |
| 护送与路线风险 | 起运前最多 4 名本国玩家在起点加入护送队。护送人数、起运/绕行后的风险快照和准备时间保存在 SQL。护送者改为承运者时，在领取事务中移除其自己的护送登记。 | 自身不参与风险、计时或具体承运者保险报价的护送优惠；其他护送者最多降低 40% 路线风险并缩短 20% 运送时间。交付遭袭则运输为 `FAILED`、实物退回起点，不生成运费结算；重运仍用相同批次风险值。护送者无独立奖金。 |
| 退回原物 | 检查背包空间，持久化唯一退还收据，按原物品数据验证保存，再销掉 SQL 批次。 | 背包不足时整批保留。保存结果不确定时冻结再次领取。 |
| 军队消耗 | 以军队、周期、资源为唯一键。库存扣减与消耗记录同事务提交。只有仍受本国控制、与军队同世界且在服务半径内的前线消费。 | 同一周期重试不会再次消费。失守或超出范围时覆盖率为 0、保留物资；恢复后沿用本周期已有记录。停服期间不会补扣历史周期。 |
| 推进前线 | `/supply front <新ID> <军队>` 在同一事务中解除旧站军队绑定并创建新站。 | 旧站库存、道路和运输合同留在原处，新站需要真实物资补给；失败则整个绑定变更回滚。 |
| 战役额外需求 | 服务线程采样 StarCore 冬季与围城状态，工作线程记录连续性，再使用同一库存消费事务。 | 已消费周期的需求快照不变；停战、围城解除、过期观察或时间回退停止压力。 |
| 承运收入保险 | 独立保单先通过 StarCore 真实预留赔款，再收保费并记入国库，全部确认才激活。 | 不确定经济阶段冻结保单及运输；只对持久化 `RISK` 原因的实际遭袭触发理赔，超时、取消或普通运费拒绝不赔。 |

StarCore 的 `NationSpendingService` 提供幂等的国库扣款和退款凭证。玩家内部经济的发款接口没有可直接重放的持久凭证，因此适配器先写入发款开始记录。重新启动后，如果只能确认调用已经开始，就将该笔转人工核对。管理员应核对 StarCore 操作凭证、玩家账目和时间，再使用 `/supply reconcile <结算UUID> <paid|unpaid>`。确认未到账时会按照同一个扣款凭证退款。

库存收据和背包同时写入 Paper 玩家存档。插件读回并同步该存档，然后提交本地 SQL。收据缺失时不会仅凭背包数量推断已经扣除或退回。管理员可结合存档与日志使用 `/supply reconcile-inventory <收据UUID> <applied|untouched>`。没有足够证据时让记录继续保留待核对状态。

当前主 SQL schema 为 v8。v3 增加跨国额度，v4 增加路线风险和护送成员，v5 增加批次遭袭值，v6 增加关税快照与阶段，v7 增加持续围城观察，v8 增加运输失败原因与不可变发生时间。`tavern.db` 使用独立 v1 schema；`insurance.db` 当前为 v2，增加真实激活时间，v1 的旧活跃保单以已有持久创建/更新时间保守迁移。未起运等待期从激活时间计算，经济阶段等待核验不会提前耗尽起运窗口。主生命周期迁移测试路径为 v1→v8；本轮完整测试与运行验收结果见 [构建](BUILD.md) 和 [Paper 记录](PAPER-ACCEPTANCE.md)。Paper 已实际验证 v5→v6 及六类物资闭环，v8 扩展运行验收单独记录。

`SupplyConsumptionEvent` 在首次消费提交后异步通知，包含本次需求和实际消耗；唯一 ID 由军队与周期确定。消费记录负责幂等，事件本身不保证在提交后崩溃时可靠重发。监听器异常不会回滚已经提交的真实消费，不能依靠事件是否收到决定再次扣库存。

含非零税额的订单把阶段保存在 `settlement_tax`：`QUOTED` 表示快照已保存，`FUNDING` 表示正在调用 StarCore，确认后为 `FUNDED`；异常或返回不确定时转 `REVIEW`。StarCore 当前 `TaxationService.fundTax` 对重复税务 ID 返回 0，且没有按交易 ID 查询税收回执的公开接口。卖家已收款而税额结果不明时，不能再支付卖家或仅凭余额推断税款状态；订单与实物批次保持冻结。管理员须从独立 StarCore 账务证据确认 `funded`，或确认未缴后通过保存的同一报价补缴，再执行对应的 `reconcile-tax` 选项。

运输遭袭在解除实物预留的同一个 SQL 事务中保存 `failure_reason=RISK` 与 `failed_at`，超时保存 `EXPIRED`。保险根据这个原始发生时间判断理赔，不以重启后的当前时间猜测，也不把所有 `FAILED` 当成遭袭。保险与主货物数据库分别提交时，维护轮询会重新连接保单和最终运输状态；确认过的款项不会因这次连接重放。保单经济阶段及 `/supply reconcile-insurance` 的证据要求见 [保险恢复](INSURANCE.md)。

主动取消运输或退保先检查货物仍处于 `OPEN/IN_TRANSIT`，再处理准备金。货物已经进入普通结算、遭袭失败、交付或关闭后，不能借退保取消既有理赔；维护过程按持久化运输结果完成保险。

路线风险扫描逐区块覆盖仓库间直线路径，包含穿越区块角点的保守邻格。超过 4096 个路径区块的道路不可规划：新建请求直接拒绝，旧记录视为封锁。这个上限防止不完整扫描把敌对占领区误判为安全路段。
